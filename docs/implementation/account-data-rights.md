# Account data export

The signed-in Account page lets an owner request each section as consecutive JSON parts. Save all desired sections and separately save the cloud design JSON and uploaded files listed in each manifest part. A requested browser download is not proof that the browser or user saved the file. Pending metadata is included, with `unavailable_pending` and no file route. Ready metadata says `ready_to_request`; an object can still be missing or invalid at download time.

## Fixed section allowlist

| Section | Included data |
| --- | --- |
| `profile` | Name and email from the verified, centrally current signed session; no owner hash or session version |
| `designs` | ID, name, archived/ready flags, created/updated timestamps, file availability and local authenticated download route |
| `links` | ID, slug, name, target, publication/archive state, created/updated timestamps |
| `scans` | Every retained daily aggregate: owned link slug, day, count |
| `pages` | ID, slug, validated draft and published version, publication/archive state, created/updated timestamps |
| `assets` | ID, name, declared MIME/size, ready flag, created timestamp, file availability and local authenticated download route |
| `feedback` | Every retained received submission through an owned page: ID, page ID, sender name/email/message, created timestamp |
| `billing_customer` | App-held Stripe customer ID and test/live mode |
| `billing_events` | App-held event ID/type/time, customer/subscription IDs, test/live mode |
| `security` | Retained event ID/type/time; latest 100 for up to 30 days |

Archived and pending records count as owner-held records. No free/paid capacity limit stops traversal. Feedback is not limited to the management UI's latest 100. Child queries restrict owner in SQL by joining the owned link, page or billing customer.

No service credentials, session versions, cookies, OAuth tokens, R2 keys, checkout session/reservation/idempotency values, raw billing provider payloads or network quota hashes are exported. User-authored design content (including a saved Wi-Fi password) is part of the private design JSON. Anonymous artwork jobs use a separate browser identity and are not associated with this account export. Local-only designs require exports from [On this device](/designs). Stripe's separately held receipts are accessed through [Billing](/billing); no Stripe request is made to prepare an account export.

## Pagination and limits

`POST /api/account/export` accepts only `{ "section": "<allowlisted section>", "cursor": null }`, then the returned opaque `nextCursor` for later parts. The body is bounded to 1 KiB and must be JSON. Exact canonical Origin is mandatory and cross-site Fetch Metadata is rejected. All browser `x-qr-*` headers and query parameters are rejected.

Each response includes `formatVersion`, `section`, `generatedAt`, `records`, `counts.records` (this part only), `nextCursor` and `complete`. Parts contain at most 25 records and at most 1 MiB of UTF-8 JSON, including the envelope/cursor. The browser saves that exact JSON, without pretty-print expansion. A bounded SQL `LIMIT 26` provides one lookahead row. A part that fills its byte budget returns a cursor after its last included record. An individually oversized row fails explicitly with 413 on the part that would include it; no row is shortened and the section is not marked complete.

Keys are immutable record IDs, customer IDs for customer linkage, `(slug, day)` for aggregates, and `(created_at, id)` for security activity. Security activity is traversed oldest first so the export's own retention pruning removes events already passed by its cursor. Cursors are HMAC-authenticated with a domain separator and owner binding, contain a section-specific key tuple, and are strictly validated for shape, key type and section. Changing owner, section or cursor bytes is rejected. No offsets, arbitrary table names or caller-defined sort/row limits are supported. Cursors have no expiry but stop working if the service secret changes.

This is a **live paginated export, not an atomic database/R2 snapshot**. Edits, newly created data, deletion and retention cleanup during traversal may change which rows appear in later parts. Restart a section if needed. Each successfully prepared page records the fixed internal `data_export` event and applies existing security-event retention. Exporting security activity itself can therefore affect the retained event set. The response does not promise a total row count across an unstable snapshot.

## Original-file downloads

`GET /api/account/export/files/design/:uuid` and `/api/account/export/files/asset/:uuid` are authenticated application routes. The browser supplies only the fixed kind and UUID. The Worker resolves the storage key from an owner-scoped row, requires ready state, reads the private object and checks both the R2 actual size and the body byte count. Design JSON is limited to 3 MiB; uploaded assets to 2 MiB. Design JSON must satisfy the existing storage validator and is serialized from its allowlisted result. Assets use `application/octet-stream`, regardless of their uploaded MIME or filename.

The Worker and application proxy read streams into bounded buffers before returning successful attachments. This deliberately trades a small bounded buffer for truthful rejection of incomplete or oversized objects, rather than beginning a successful partial download. Reads have a 10-second deadline; application service requests have a 15-second timeout. The browser fetches one chosen file at a time. It never automatically starts all listed downloads.

Responses use server-generated kind/UUID filenames, attachment disposition, private/no-store, nosniff, no-referrer and a sandbox content policy. No uploaded filename is used as a response header. Pending records return 409, absent owner rows or missing objects 404, oversized size metadata 413, invalid/incomplete/actual-byte-over-limit files 422, and infrastructure failure 503. These are per-file outcomes; metadata export never claims all originals are available or saved.

## Account validation and failure behavior

The application uses the reviewed `currentSession` lookup before each page/file operation. Its service request contains a server-derived owner and signed session version. The Worker dispatcher verifies the service bearer; the export handler independently checks the owner/version in `account_security`. A valid bearer plus a revoked/missing account gets the exact owner-bound `409 account_session_invalid` denial. The application maps only that exact denial to browser 401. Bearer rejection, malformed denial, D1/R2 failures and unavailable account security return 503 without clearing cookies or claiming logout.

No new event HTTP endpoint, export storage bucket, public share link, CORS policy or provider integration is introduced. Export contains no billing entitlement lookup and remains available after downgrade or while Stripe is down. The UI keeps only bounded current manifest entries and per-section cursors/counts in component memory, aborts pending requests on unmount, and is remounted on account change and removed on sign-out. It writes no personal export contents to browser storage.

## Validation

`tests/account-export.test.ts` uses in-memory real SQLite with every production migration, two owners, the production Worker dispatcher and the production application proxy. It covers multipart traversal, >100 feedback, tied aggregate keys, archived/pending/empty sections, both row/UTF-8 byte boundaries, owner and cursor attacks, CSRF/header/body attacks, bearer/session failures, safe attachments, private object absence/size/malformed data, actual-byte validation and outages. The focused suite is run together with the reviewed account/session suites. No provider, production data or credentials are used.

## Permanent self-service account closure (Task2c)

The Account page now presents the exact losses before sending an authenticated, exact-origin JSON confirmation to `POST /api/account/deletion/verify`. Only `{ "confirm": true }` is accepted, with a 1 KiB/5-second body bound; query parameters and browser `x-qr-*` identity headers are rejected. Google PKCE, state, nonce, verified email, authorized party and canonical callback checks remain. The OAuth cookie carries a separate deletion action bound to the current owner/session version. `max_age=0` requests fresh authentication, and the callback requires a verified `auth_time` within five minutes, matching the initiating attempt. A different Google identity, changed session version, missing freshness claim, ordinary login or URL flag cannot approve closure. Real Google behavior remains a provider verification task; the fixture verifier does not establish provider or browser proof.

Successful verification records a random one-time owner/version intent in D1 for five minutes and redirects to the Account page for the final explicit confirmation. It issues separate HttpOnly purpose-bound cookies: a five-minute destructive intent and a thirty-day status-only receipt. The receipt is issued **before** acceptance so a lost response is recoverable even though all sessions become invalid. It authorizes only an owner/intent status lookup; it cannot read account content or start an unaccepted deletion. Ordinary successful login clears stale closure cookies. Closing permanently disables subsequent registration for that Google identity; no recreation or support workflow is invented.

`POST /api/account/deletion` accepts the same fixed confirmation schema. The application derives owner, version and intent from signed cookies, validates the current central session, and inspects persisted billing even when `BILLING_ENABLED` is false. With a binding, it validates the configured Stripe mode, exact customer ID and owner metadata, up to 100 fresh subscriptions and up to 25 checkout sessions; provider pagination, mismatches and unknown state block closure. Every status other than `canceled` or `incomplete_expired` blocks, regardless of known price or entitlement. Scheduled cancellation is still active until the subscription actually ends. Open/processing sessions, live leases, unresolved create reservations and provider failures block. Completed checkout retirement requires its associated terminal subscription and a second fresh all-subscription check; expired sessions also require the fresh check. Retirement compares reservation, session ID, revision and expired/no lease. No provider subscription cancellation, refund or checkout expiry is performed.

The Worker accepts only service-bearer calls. Acceptance uses a real D1 batch transaction to consume the exact intent, mark the account closed, increment its session version and create its deletion job. The transaction matches the exact inspected billing binding/revision and requires no reservation, checkout session or lease. New billing customer/reservation writes increment the revision and SQL triggers reject closed owners. A concurrent checkout therefore either precedes acceptance and blocks it, or follows acceptance and is rejected. The minimal billing binding and event history remain, rather than orphaning billing records. Requests concerning active subscriptions still require the operator's separately reviewed rights process; the self-service guard is not a ruling on legal entitlement.

## Access fences, cleanup and honest progress

Migration `0007_account_lifecycle.sql`, after `0006`, defaults existing accounts to active. Legacy public records whose owner has no `account_security` row remain available. Public page, asset and redirect SQL reads explicitly exclude closed owners; triggers also fence public feedback and scan counts and every owned content/link/cloud/billing mutation. Application proxies send the centrally checked signed session version; the Worker checks it for private content and billing mutations. Closed identities are denied regardless of token version. An already running response can finish; subsequent requests cannot regain content access.

New cloud objects use `accounts/<owner>/g1/...`; new uploaded assets use `content/<owner>/g1/...`. Generation `g1` stays fixed because recreation is unavailable; the independently increasing session version revokes login tokens. Before each R2 put, an owner/version/key journal is durably inserted. A confirmed put is settled only with a post-write lifecycle check; a close racing the put adds remaining cleanup work and cannot revive a row. Keys are checked for other references before object deletion. Uncertain put acknowledgements remain pending: the implementation does not infer that a timeout means nothing was written.

Each existing hourly scheduled invocation selects at most five deletion jobs. Each job journals/removes at most 25 cloud rows and 25 asset rows in transactional batches, processes at most 25 settled upload records, 25 submissions, 25 count rows, 25 pages, 25 links and 25 security events, lists at most 25 R2 objects from one of two owner prefixes, and attempts at most 25 manifest removals. Child rows are removed before their parents. Manifest insertion precedes D1 reference removal in the same transaction, including pending rows. Legacy random `content/<uuid>` keys are captured from owned asset rows; unreferenced legacy random keys cannot safely be attributed and are not indiscriminately deleted. Old cloud-version orphans are covered by the owner prefix. No QR payloads, filenames, email, feedback or credentials are written to deletion logs/receipts.

Independent private R2 ledger persistence must succeed before any content metadata is removed. A storage failure leaves the remaining journal intact for retry. A manifest key referenced by another owner is preserved and keeps cleanup pending. A genuinely uncertain upload journal also keeps cleanup pending even after every currently visible object is removed. Closed tombstones remain in bounded sweep rotation even after completion so later orphan objects are rediscovered. `complete` means the last completed owner-prefix traversal and durable work checks found no remaining owned content or unsettled uploads; it is not a claim about provider backups or copies outside active application storage. The UI distinguishes accepted closure from pending/complete content cleanup and offers receipt-based status checks. It clears session cookies only after confirmed acceptance; unavailable/uncertain responses keep cookies.

## Exact remaining records and retention decision

The engineering implementation retains these records; their final retention periods still require owner/legal approval before public release:

- `account_security`: owner hash, monotonically increased session version, closed lifecycle and deletion ID. Permanent in this implementation to prevent identity/session revival.
- `account_deletions`: deletion ID, owner hash, revoked version, acceptance timestamp, ledger-ready/completion flags, bounded sweep prefix/cursor/check flags and last-sweep timestamp. Permanent tombstone and retry bookkeeping; completed jobs continue periodic reconciliation.
- Private `deletion-ledger/v1/<owner>/<id>.json`: format version, owner hash, deletion ID, revoked-through version, acceptance timestamp and closed flag. Independent of D1 backups; retained indefinitely pending an approved retention schedule.
- While unfinished: `account_uploads` owner hash/session version/storage key/pending-or-settled state and `account_deletion_objects` owner hash/storage key. Settled cleanup rows are removed after acknowledged object deletion. Uncertain rows are not expired automatically.
- `account_deletion_intents`: random ID, owner hash, session version, expiry and consumed flag. Five-minute intent validity; hourly cleanup removes up to 100 expired rows per invocation.
- Existing `billing_customers`: owner hash, Stripe customer ID/mode and revision, with reservation/tier/reserved-at/session fields null and lease zero after safe acceptance. Existing `billing_events`: ID/type/time, customer/subscription IDs and mode. No financial payloads or payment credentials are added; provider financial records remain separate.

Owned short-lived security events are removed through bounded cleanup. Anonymous artwork/browser identities and aggregated network quotas cannot be attributed to the account; their existing separate retention still applies. Local/device exports, downloaded copies, recipient devices, caches, search engines, third-party provider records and backups are outside this active-storage deletion. This is an engineering control, not legal certification or a substitute for operator rights handling.

### Billing customer setup fence

Before the existing Stripe customer-create call, the application now persists `billing_customer_creations` with owner hash, mode, random reservation token and creation timestamp. Both the authoritative closure precheck and the final D1 acceptance transaction reject any outstanding row, including when no customer binding exists yet. A closure that wins first blocks this insert through a SQL trigger, so the provider call cannot start. A customer create that wins first blocks closure until the exact verified mode/customer binding is persisted and the reservation is cleared. Retries preserve the existing deterministic provider idempotency key; a creation older than 23 hours is not automatically replayed. Only an acknowledged Stripe 400 metadata-validation rejection releases the exact reservation token. Network failures, idempotency conflicts, other provider errors and uncertain outcomes remain pending. These content-free reservation fields are retained until successful binding or explicit reconciliation; they cannot exist on an accepted closed account.
